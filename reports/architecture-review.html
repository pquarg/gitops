Problem

The operational interface spans commands and UI actions across three files; resource names and ordering leak into the operator’s work.

Solution

Give repeated backup and release verification behavior one app-owned implementation, retaining short runbooks for decisions and recovery.

  • Locality: one release sequence
  • Leverage: reusable verification
  • Depth: less operator knowledge
Seam / adapter: keep the operational seam inside the app; use the current kind adapter and introduce an RDS adapter when RDS exists.
Test surface: exercise the operational interface in disposable kind, including failed backup and failed migration; an archive read check still needs a real restore test.
Deletion test: duplicate procedural knowledge leaves the runbooks; adding a pass-through module that sends operators back to the same instructions creates no depth.
Scope: start with backup and verification. Automating live sync needs a reviewed Git revision and defined failure behavior; reset and recovery decisions remain explicit. Existing sync waves already order the rollout. Argo CD sync phases and waves.

Problem

The validator checks names, rendering and schemas, while routing, storage binding and this app’s migration correctness depend on relationships between manifests.

Solution

Concentrate a small set of real deployment invariants at the existing app-root seam; keep FastAPI migration rules app-owned and database-free apps valid.

  • Leverage: every future app
  • Locality: one validation entry point
  • Depth: whole-deployment guarantees
Observed: both current Kustomizations render successfully. A temporary copy with the app’s traffic selector changed to an unmatched value also renders successfully. The existing validator adds schema checks, but contains no relationship check for this mismatch.
Seam / adapter: deepen the existing validation interface; kubectl rendering and kubeconform remain its current tool adapters.
Test surface: check real malformed rendered deployments, a database-free app, and this app’s image / Secret references and storage binding; avoid per-app policy configuration.
Deletion test: shared validation earns its keep across local and CI callers; deleting it distributes review work. Deepen it instead of adding separate per-manifest modules.
Tradeoff: keep the implementation small. Offline checks cannot prove live Secret presence, image availability or database compatibility. Schema validation is one part of the result. kubeconform documentation.

Problem

Every new database repeats laptop paths, node affinity and cluster-wide PV binding details even though its database is app-owned.

Solution

Explore a storage implementation that absorbs local placement and provisioning while each app keeps its database and requested storage.

  • Locality: cluster storage mechanics
  • Leverage: less database onboarding
  • Depth: placement hidden from apps
Seam / adapter: the Kubernetes storage seam is real; replace the local provisioning adapter only if it earns its cost. No new provider interface is proposed.
Test surface: provision storage, replace Pods, retire claims, then rebuild kind and recover the original data through the same storage interface.
Deletion test: deleting static PV manifests alone moves the work to the operator; depth improves only if the storage module actually absorbs placement and retention.
Decision gate: a provisioner adds a dependency and changes recovery semantics. Preserve data across kind rebuilds before adopting it. Current local volumes require static PVs, so this needs a different provisioning implementation. For one database, keeping the current static manifests may be simpler until RDS. Kubernetes local volumes.
Constraints that narrow the work

The existing structure earns its keep

  • Root + ApplicationSet: automatic app discovery and shared registration updates already work through Git; deleting the root moves those updates to the operator.
  • App-owned databases: Postgres, migrations, backups and runbooks already live with the app. Preserve that locality.
  • One current app: wait for real repetition before adopting a generic Helm chart, shared app template or onboarding generator.
  • Legacy migration guard: keep it until the default namespace cutover is confirmed; it protects retained data from a second Postgres.

Keep the AWS move concrete

  • Database seam: AUTH_DATABASE_URL is already app-owned and shared by the workload and migration Job.
  • RDS cutover: plan data transfer or recreation, network access, TLS and backup changes before retiring local Postgres. RDS PostgreSQL connection requirements.
  • EKS: replace the current kind storage and localhost ingress implementation when the target exists; keep app discovery and app-owned migrations.
  • One adapter now: planned AWS targets do not justify a generic cloud interface today.
Existing deletion policy: app auto-pruning is off and Application deletion preserves deployed resources. That means Git removal still needs deliberate cleanup; retained PV/PVC protections are separate. Revisit ordinary workload pruning only with clear retirement expectations. ApplicationSet deletion · Per-resource retention.
